How much, and how well, does firetower ship?

Specification for a shipping-metrics page on the private dashboard, beside telemetry.

Status awaiting approval Discovery map #399, 7/7 resolved Prototype #406, approved Lands in backend · firetower-terraform Written 2026-11-18
decided settled in discovery, with the owner proposed recommendation, needs validation unresolved discovery did not answer it

Problem

The firetower project ships continuously and almost entirely through AI agents, and there is no objective record of how much or how well. The owner's sense of productivity comes from impressions — a busy week feels productive — which is exactly the thing that an agent-driven workflow distorts: output volume can rise while quality falls, and neither is visible.

The existing telemetry dashboard answers how is Firetower used. Nothing answers how is Firetower built. The data to answer it already exists — conventional commits are enforced in CI, release-please tags every release, and GitHub holds every pull request — but it is only reachable by hand, one gh command at a time.

The audience is the owner alone decided. This is an instrument for one person deciding how to work, not a report for anybody else.

Proposed solution

A second page on the existing private dashboard, reading from GitHub data about firetower-cloud/firetower ingested into Postgres on a daily schedule. It shows two loops — work reaching main, and work reaching a user — with the gap between them as the headline, each number compared against the project's own recent history rather than an industry benchmark.

It inherits the telemetry dashboard's access model unchanged: no login, nothing published, reached through an authenticated Cloud Run proxy by named principals.

The constraint that shaped everything

Three of DORA's metrics do not survive contact with this repository as normally defined, and discovery was mostly about finding what does work. Reverts are too rare (four in 1,546 commits). Bug labels are unreliable (79 of 141 issues unlabelled). PR lifetime is not where the work is (median open-to-merge 40 minutes — the agent finishes on the branch, then opens the PR). And the stability half of DORA happens on installs this project gets no telemetry from, because Firetower is self-hosted.

So this specification deliberately reports less than a DORA dashboard would, and says on the page where a number is unavailable rather than deriving a plausible one.

User experience and requirements

The headline

The merge→release gap is the headline number decided — how long work that has reached main waits before a user can install it. The prototype established this empirically: its 28-day rolling median moves between 0.26h and 73.0h across the project's life, and no other series shows comparable movement. Every alternative was either saturated or gameable; merges-per-week has the widest band and is the easiest to inflate by splitting work.

Four tiles, on the telemetry page's existing grid decided:

Lead time (first commit on the branch → merged) stays available below the fold rather than in the headline row decided. Three of the four tiles currently read worse than the project's own normal, which is the evidence that this is not a page of flattering numbers.

Granularity

Weekly is the default; the same figures must also be computable per month decided. Because the schema stores event rows rather than daily rollups, this is a date_trunc over data already present.

The three quantities, and the rule that governs them

Failure is not one number here. It is three, and the page must never average or merge them decided.

QuantityDefinitionSampleMay be called
Escaped — reported A bug report filed by somebody who is not the owner, identified by the bug label 6 in 15 weeks a failure
Escaped — derived fix commits touching code already present in a release hundreds a failure, but not a rate
Rework All fix as a share of feat+fix 755 commits a process metric only

Two labelling prohibitions, and they are requirements

  • Rework must never be labelled a failure rate. A fix to code that never reached a release is the process working. Rework counts those, so presenting it as failure would state something false — and it would penalise fixing things promptly, which is the behaviour this page should not discourage.
  • The derived-escape axis must not use the word "rate". It runs at 13.1 fixes per release event and has never been below 1.16. It is a density, not a percentage, and "a change failure rate of 1,310%" is not a number.

Rework is an instrument, so it has to be actionable

Rework earns its place because a rising figure would change how the owner runs the agents — prompts, review gates, test requirements before merge decided. A single blended percentage cannot support that decision, so it is broken down by conventional-commit scope, which is a property of the work rather than of who did it. Measured over 28 days: server 76%, mobile 72%, desktop 57%, no-scope 36% — a 44-point spread at n≥25.

The scope vocabulary is not the documented one

CONTRIBUTING.md names ten scopes. The commits use 49 — desktop 216, mobile 125, server 88, web 67, island 28, schedules 14 — while two documented scopes have one and three commits respectively. The breakdown must be data-driven with a minimum-n floor decided, never coded against the documented list, or it will show empty bars for scopes nobody uses and omit the busiest ones.

Time to fix

From the release that shipped the defect to the release that fixed it — and measured only where that is knowable decided, which is the externally-reported axis, where the issue's creation date bounds when exposure began.

It is not computable for the derived axis: only 65 of 411 fix commits reference an issue, and none names a version or identifies itself as a regression. The derived axis therefore reports a count and a density but no duration, and the page states why rather than inventing one.

Three ways of inventing it were considered and rejected decided: git blame attribution (fragile exactly where it matters — a formatting pass reassigns authorship of untouched logic); assuming the previous release (wrong precisely for defects that survived several releases, which are the worst incidents); and enforcing a Fixes-release: commit footer (genuinely attractive, since enforcement is proven to work here, but it changes behaviour instead of measuring it and starts with no history — worth revisiting once the page exists).

Unresolved bugs are shown, not excluded

The median over closed bugs appears with "N still open, oldest X days" as a permanent companion figure decided. Two of the six are open and one took 472 hours; a closed-only median would report a healthy ~14 hours over an invisible third of the sample.

A deployment is a release event

81 release events, not 129 tags decided. The grouping rule is the target commit SHA — release-please cuts every tag in a run from one commit — giving 52 single-package events, 12 two-package and 17 three-package.

An ingest correctness rule, not a tidiness preference

Of the 129 GitHub releases, two are rolling tags — worker-latest and desktop-latest — whose target_commitish is the literal string main rather than a SHA. An ingest grouping by target without first filtering to <pkg>-v* would collapse every day those tags were re-pointed into a single bogus release event, corrupting deployment frequency and every "first release containing this commit" answer derived from it.

Comparison: the project's own history, not an industry band

No elite/high/medium/low bands decided. DORA retired them in its 2025 edition; the last numeric bands are from 2024, there is no 2026 survey edition, and pages titled "DORA Benchmarks 2026" are SEO content. Discovery also found the bands would be meaningless here for a structural reason: the same 15 weeks reads High at 81 release events and Elite at 129 package tags — a figure that swings two bands on a definition choice is not a measurement.

Instead: a 28-day trailing baseline, median not mean, a daily rolling sparkline per tile, and a shaded IQR-of-all-history band — "normal for us" — occupying the visual role a performance band would have taken. DORA's own current text supports this: "the best, most insightful comparisons of software delivery performance are for the same application or service over time."

The two discontinuities

The dataset contains two process changes that a naive trend line would report as productivity improvements. Handling them is a correctness requirement, not a presentational nicety decided.

DateWhat changedEffect on a naive chart
~2026-09-25Work began going through pull requests 155 of 369 trunk commits (42%) came through no PR, all before this date — any PR-derived metric reads near-zero for the first six weeks
2026-11-09
13:06:58		 commits.yml began enforcing conventional commits Untyped commits go 8.8% → 0%, so feat/fix counts step up for reasons unrelated to shipping

The untyped commits are a spike, not a background rate: 99 of the 115 fall between 2026-10-26 and 2026-11-09, 72 in the week of 2 November alone, against a prior run rate of one to five a week. The spike is almost certainly what provoked the enforcement workflow.

Truncating history at 2026-11-09 was rejected — it would discard 93% of a usable history and pin rework at a nine-day figure of 77%. The treatment instead, prototype-derived decided:

  • Two thin dated rules on every time axis, marking both dates.
  • A dashed segment wherever a series' own input coverage is incomplete — keyed to measured coverage, not to the date, so it is correct for each series independently.
  • The missing input plotted, not annotated: a grey wash from the top of the rework chart showing that 17% of the current 28-day window carries no commit type at all. It clears on 2026-12-07, when a 28-day window finally passes enforcement day.

Because the audience is the owner alone, other caveats are discharged by a footnote or a tooltip rather than a tile or a banner, and the page optimises for information density over self-explanation. The discontinuity markers are exempt from that relaxation — they are correctness, not explanation.

The page polices its own inputs

Two states must be visible on the page itself, because both are failure modes that otherwise look like good news:

  • "Last ingested at", with a loud state when stale decided. A dashboard quietly showing a fortnight-old number is worse than one admitting it could not read — the position the telemetry page already takes by rendering per-panel errors rather than throwing. The displayed freshness is the oldest successful dataset, not the newest.
  • "External issues not yet classified: N" decided. The reported-escape axis depends on the owner labelling externally-filed bug reports. If the habit lapses, the defect count falls — and without this figure that reads as improving quality rather than as missing data.

Tables stay

Every plotted value remains reachable as text decided. This is an inherited obligation, not a preference: globals.css permits one low-contrast series specifically "because every plotted value is also a direct label on the chart and a row in the table below it, so no number is reachable only by telling colours apart." A page that drops the tables invalidates that reasoning for the whole design system.

Acceptance criteria

  1. The page renders four headline tiles — merge→release gap, releases per week, rework share, escaped-to-a-user — each with a 28-day trailing median, a daily rolling sparkline, and an IQR-of-all-history band.
  2. Every figure on the page is also available per month, not only per week.
  3. No element of the page displays an elite/high/medium/low band or any industry benchmark.
  4. Rework is labelled as a process metric. No element labels it, or the derived-escape density, as a failure rate.
  5. Rework is broken down by conventional-commit scope, derived from the data with a minimum-n floor, and shows the current spread against each scope's all-history figure.
  6. Both discontinuity dates are marked on every time axis, and any series whose input coverage is incomplete for part of its span renders that part as a dashed segment.
  7. The rework chart plots its own missing-input share, and that share reads 0% for windows beginning on or after 2026-12-07.
  8. Deployment frequency counts 81 release events for the project's history to date, and the ingest excludes tags not matching <pkg>-v*.
  9. Time to fix is reported only for externally-reported bugs, with "N still open, oldest X days" displayed beside the median. The derived axis shows a count and a per-7-day density and no duration.
  10. The page displays a last-ingested timestamp reflecting the oldest successful dataset, and renders a visually distinct stale state when it exceeds the ingest cadence.
  11. The page displays a count of externally-filed issues carrying no classification label.
  12. Every plotted value appears as text in a table on the same page.
  13. A failed query renders an inline error for its own panel; the rest of the page still renders.
  14. The ingest runs daily on a schedule, and can be executed on demand by a principal holding run.invoker on the job, without a deploy.
  15. A run that fails for one dataset and succeeds for others records that per dataset, and the page reflects the failure rather than the successes.
  16. The dashboard's Postgres role can read every new table without a manual grant after the tables are created.
  17. The page is legible at 380px width and in both colour schemes.
  18. queries.sql contains the queries the page runs.

Implementation decisions

Where the ingest runs

A Cloud Run Job driven by Cloud Scheduler, daily at a fixed UTC hour decided, in the existing production project and region. The manual trigger is job execution itself — a Cloud Run Job is executable on demand by definition, so "daily plus a manual trigger" needs no endpoint, no button and no extra mechanism, only run.invoker granted to the same principals that already read the dashboard.

Settled on credential direction: the database write credential never leaves the project. The rejected option — a scheduled GitHub Actions workflow — does work (the Cloud SQL Auth Proxy is a client-side program and "provides secure access to your instances without a need for Authorized networks"; authorized networks are the alternative to the proxy, not a prerequisite for it) and needs less infrastructure, and it is the only scheduling mechanism this estate already operates. That cost is accepted knowingly: this introduces the estate's first scheduler. An in-process timer on the dashboard service is rejected outright — it costs roughly $45/month and does not run at all when the service scales to zero.

No GitHub credential is required decided. The repository is public and all twelve endpoints the ingest needs answer unauthenticated, so there is no token to store, scope or rotate.

Architectural boundary

The ingest is a crate beside the existing ingest service over the same database, never a route on it decided. The public endpoint's design is that it can insert a digest and do nothing else — no read route, no parameter reaching the database — and that property is preserved rather than traded.

Data model

Event rows, not daily rollups decided; one row per pull request, trunk commit, release, release event, workflow run and issue, in the existing telemetry database under a dora_ prefix. The entire history is a few thousand rows, so there is no storage or performance argument for rolling up — a rollup would only foreclose questions nobody has asked yet, and the monthly-granularity requirement is already an example of one arriving.

Columns that are easy to get wrong, each one a correctness matter:

ColumnWhy it is not the obvious choice
author date, not committer date They differ on 11.1% of commits — a rebase or amend moves the committer date, so a "when was this written" series drifts for a tenth of the data
head ref on pull requests The release-PR identifier is the head ref prefix, which selects all 82; title matching selects only 42, because the template changed mid-life
trunk position Every versioned release target sits on main's first-parent chain, so "the first release containing this commit" becomes an integer comparison rather than an ancestry walk
release event id Groups package tags into the 81 events that are the deployment unit, while keeping the package dimension answerable

Derived metrics live in SQL views decided. The telemetry page does its arithmetic in application code, which is right for a grouped count and wrong for a 28-day trailing median, an IQR band or a windowed density.

Raw payloads are kept decided, and the reason is asymmetric: pull requests, commits, releases and issues can be re-read from GitHub at any time, so keeping them is insurance — but workflow runs cannot. GitHub documents 90-day retention for runs in public repositories, so for that one table the stored copy is the primary source rather than a cache. That asymmetry belongs in a schema comment, because a future reader deciding whether to prune needs to know it.

Database roles — a verified trap

Migrations run as the database owner; the ingest cannot create tables

The dashboard's read-only role relies on a default-privilege grant that the README describes as what "stops a table added later from being invisible to the dashboard". These are the first tables added since that was written, so it was tested against a real Postgres 17:

Table created byDashboard role can read it?
the database ownerYes — the documented claim holds, no manual grant needed
a separate ingest roleNo — permission denied

Default privileges are scoped to the creating role. So migrations run as the owner and the ingest connects as a role holding insert/update/select on the dora_ tables and no create. The alternative — migrations as the ingest role plus a second default-privilege statement — is one forgotten statement away from a silently blank dashboard, which is the exact failure the README's paragraph exists to prevent. No change to the documented grant block is needed.

Run marker

One row per dataset per run decided — which dataset, when, success or failure, rows written, and the error if any. A single success boolean spanning six datasets would hide the failure that actually matters: pull requests ingesting happily while workflow runs fail for a fortnight, under a cheerful "last ingested" timestamp.

Documentation change

The backend README states "counts, never records about people or their work" and "There is no row per person anywhere in this database". The second stays true — there is no author dimension anywhere in this specification. The first becomes false, because the new tables hold commit subjects and pull request titles, which are records about work. Proposed replacement wording is with the owner for approval proposed. The identity-contract test is unaffected either way: it guards the telemetry digest payload, which none of this passes through.

Incidental fix

The prototype found that a 1000-unit viewBox scaled into a 390px frame renders 11px axis text at roughly 4px. The fix is two CSS rules re-sizing SVG type in user space at the breakpoints, and it improves the existing telemetry page unchanged proposed — worth shipping with this work rather than separately.

Testing strategy

Test through the highest meaningful seam, and prefer asserting the things discovery found easy to get wrong over asserting that code runs.

Ingest correctness — the highest-value tests here

  • Rolling tags are excluded. Given a release set containing tags whose target is a branch name rather than a SHA, release-event grouping must not merge unrelated days. This is the single most consequential ingest bug available, and it is invisible in the output unless asserted.
  • Release-PR identification by head ref, asserted against a fixture containing both title templates — a test that passes on title matching alone is the bug.
  • Author versus committer date preserved distinctly for a rebased commit.
  • Idempotency: running the ingest twice over the same window leaves the same row count and the same derived figures.
  • Partial failure: one dataset failing records that dataset's failure and does not mark the run successful.

Metric definitions, as SQL-level tests over fixtures

  • A fix commit on unreleased code does not count as an escaped defect; the same commit after the release containing what it fixes does.
  • Rework includes unreleased fixes; the escaped axes do not. A fixture where the two diverge, so a regression collapsing them fails.
  • A window containing untyped commits reports a coverage share below 100%, and a window starting after enforcement day reports exactly 100%.
  • Open bugs are excluded from the median and counted in the companion figure.
  • 81 release events for the project's history to date, from the real data.

Page behaviour

  • A failing query renders its panel's error and the remaining panels still render — the existing page's pattern, which has a test seam already.
  • A stale last-ingested timestamp renders the loud state; a fresh one does not.
  • Every plotted series has a corresponding table, asserted structurally rather than by eye, since the design system's contrast reasoning depends on it.
  • Renders at 380px and in both colour schemes.

Infrastructure

  • The dashboard role can select from a newly created table without an explicit grant — the trap above, kept as a test rather than a memory.
  • The scheduler role prerequisite is a documented manual step, not a test; see below.

Out of scope

  • Any repository other than firetower — not the backend, the Terraform, or the website.
  • Per-author, per-person, and human-versus-agent attribution. Ruled out: it would put named-person rows in a database whose documentation says there are none, and the owner confirmed the project-as-one-system reading was deliberate.
  • Measuring the owner's personal productivity, or leverage per unit of input — output against sessions started, agents dispatched or active days. The original request said "measure my productivity"; the divergence was raised directly and the project reading confirmed.
  • Any change to how the dashboard is authenticated or reached. It inherits the existing proxy and reader list unchanged.
  • Alerting, digests, or feeding these numbers back to agents. A dashboard is a thing you look at.
  • Industry benchmark comparison of any kind.

Open questions and assumptions

unresolved Does CI health belong on this page at all?
Workflow success rate on main, time-to-green, flake rate. Discovery left this open and explicitly rejected CI failures as the change failure rate. The history has been captured as insurance — 3,196 runs back to the first, committed to a research branch — because GitHub's 90-day retention would have made the decision moot. Note that the 411 failures are overwhelmingly branch runs, which is CI working; any "how often is main red" figure must filter on the trunk first.
unresolved Does the sparse-signal treatment survive the next burst?
The reported-escape axis was characterised during discovery as "one every 18 days". That is wrong in shape: five of the six arrived within four days, then 56 days of silence. It is bursty, not periodic, so a rate over any window is close to meaningless and even a cumulative line implies a tempo that is not there. The prototype chose a treatment; whether it reads correctly when the next cluster arrives is unknown.
proposed The README wording
Replacement text for the "counts, never records about people or their work" sentence is with the owner. It is a judgement about documentation in his voice, not a measurement.
proposed Revisit a Fixes-release: commit footer
Rejected for now because it changes behaviour rather than measuring it and yields no history. Worth reopening once the page exists and the cost of the missing duration is felt rather than argued about — enforcement is proven to work in this repository.
assumption Unreachable commits remain fetchable
Lead time from the first commit on a branch depends on squash-merged commits surviving branch deletion. This was measured — 34 commits unreachable from every ref, all still returned by the API, the oldest 49 days old — but GitHub documents no retention guarantee for unreachable objects. The daily cadence is therefore a preference today; if this assumption ever breaks, cadence becomes a correctness constraint.

Three prerequisites owned by the owner, not by implementation

  1. Grant the scheduler role and re-run the bootstrap script. The Terraform CI service account holds ten roles and cloudscheduler.admin is not among them, so the first apply declaring a scheduler job fails on permissions. Run-admin already covers Cloud Run Jobs and CI can enable the API itself, so the gap is exactly one line — but it must be added and the script re-run by an owner, before the first apply. Five minutes, and it silently blocks everything behind it if nobody knows.
  2. Backfill six bug labels. Not one of the six externally-reported bugs carries a label, and titles do not separate them from the fifteen feature requests. Without this the reported-escape axis has no input, and the page's own "not yet classified" counter is what keeps it honest afterwards.
  3. Approve or veto the README wording.
